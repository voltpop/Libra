Libra software map

The components, types, functions and relationships of the Libra firmware, derived from the Software architecture section.

Status: draft, a proposed design. Nothing is built. The firmware is C on ESP-IDF, so a "class" is a component: a header, an opaque handle or struct, and a set of lb_* functions. Signatures are sketches, not final. Generated from tools/softmap_data.py by tools/build_softmap.py, which refuses to build if the data breaks the layering rules.

Map

Click a component to draw its relationships. The map has the six layers of the architecture, top to bottom. Red outlines mark components that handle untrusted input.

Conventions

  • Component = firmware/components/<name>/ with a public header include/lb_<name>.h. Everything public is prefixed lb_.
  • Calls go down. A component may call the same layer or a lower one, never higher. The call graph has no cycles.
  • Callbacks go up. Lower layers reach higher ones only through a handler the higher layer registered (lb_*_set_*). The transports and drivers work this way.
  • Errors are returned as lb_err_t. Anything that parses untrusted input (qrparse, usb, openpgp, fido, storage, ble, qr, xch, usbhost) validates every length and is fuzzed on the host.
  • Secrets live in internal RAM where practical and are zeroized after use. Logs never contain secrets or PINs.
  • Approval is only ever granted by session. No other component decides whether a request is approved.

Open points

Event modelProposed, not yet approved: the UI never calls crypto or keystore directly, and every sensitive request goes through session. This map already follows that rule. It does not define a shared event queue.
Counter storagelb_ks_attempt_begin and lb_ks_counter_advance write before every check or code. They need a journalled, wear-levelled record that survives power cuts, with a stated write budget (verify flash endurance).
Firmware updateNo component owns the update flow yet. boot has the slot calls, but something has to receive a signed image over USB or BLE and check it. Likely a small update component.
Host tool interfaceThe v0 command-line tool (time sync, backup, update) needs a way to reach the device. The composite already uses 5 IN and 3 OUT endpoints, so a vendor interface may not fit. A custom CCID command set is the likely answer (decision needed).
Core assignmentCore 0 and Core 1 are stated for USB, crypto, keystore, Vault, UI, camera, fingerprint and BLE. session, oath, xch and backup are proposed here and unconfirmed.
Logging ruleNo secrets or PINs in logs; release builds log minimally. Not yet written into the architecture.
Security architectureThat section has not been reviewed yet. Types such as lb_level_t and the keystore API may change when it is.
Repository layoutThe component list in the repository-layout block of LIBRA.md omitted storage, vault and usb. Fixed with this map.
Reused firmwareIf the pico-fido family is adopted, openpgp, fido and oath become thin adapters around it and their internals will differ from this sketch.
